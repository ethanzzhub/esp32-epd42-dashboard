### 数据源：从东财单标的 → 东财批量 → 最终新浪

1. 起初东财单标的接口 `stock/get?secid=100.N225`，字段口径 f43=现价、f169=涨跌额、f170=涨跌幅，都要 **÷10^f59**。支持 JSONP `&cb=`。
2. 我曾误判为「1/3 概率空包」，实为 **IP 级限流**：密集请求后整个域名对该 IP 返回 `code=000 / size=0`，数分钟不恢复，连 A 股 secid 一起失效。腾讯同段正常（对照组）。
3. 改批量接口（一次 63 个全球指数，未被限流）：
   `https://push2.eastmoney.com/api/qt/clist/get?pn=1&pz=100&po=1&np=1&fltt=2&fs=m:100&fields=f2,f3,f12`
   `fltt=2` → f2/f3 已是最终值，不用再除。**坑：这里的 NDX 是纳斯达克综合（26169）不是纳指100（29273）**，美股必须继续走腾讯。
4. 10-29 在公司网络下东财整段被限流 → **日经/韩股改走新浪** `znb_NKY` / `znb_KOSPI`（明文 HTTP + Referer），东财降为兜底。

### 固件健壮性重写

- `urequests` 全部移除（无 timeout，目标机不响应会**卡死主循环**），改自写 `http_get()`：裸 socket + 硬超时 + HTTP/1.0 + `Connection: close`，最多读 4096 字节。
- `send()/recv()` 而非 `write()/read()`（老固件没有流式方法）。
- TLS 双路兜底：先 `SSLContext(PROTOCOL_TLS_CLIENT)`，失败退 `ssl.wrap_socket`。
- 新增 `_keep()`：偶发缺失的标的沿用上次值，格子不变 `--`。但 `_from_server()` 里**不能**用（否则空数据被旧值补满，上层误判服务正常而不回退）。
- 纠正过一次自己的错误说法：MicroPython 的 ssl **默认不校验证书**（无 CA 包），所以「NTP 没对上 HTTPS 就失败」是错的；真实代价只是握手 0.5–1.5s + 30–40KB RAM。

### 架构决策：板子直连，不走家里服务

- 用户问「服务跑家里 vs 板子自己拉」。早先我推荐家里服务，理由是省 TLS；**但板子在公司后这条不成立**——家里服务只能经隧道暴露，隧道本身也是 HTTPS，TLS 次数两边都是 1。
- 直连：2 次请求 / 1 次握手 / ~1.5s / 故障点 2 个。家里服务：1 次请求 / 1 次握手 / ~1.1s / 故障点 6 个（+家里断电/断网/隧道挂/Mac 睡眠）。**差 0.4 秒换四个故障点，不值。**
- 固件加了 `quote_pref`：0=直连优先（默认，缺格才补服务器），1=服务器优先。已验证 6 种分支。
- 家里服务真正不可替代的用途只剩：人不在家时手机看行情、AI 简报页（要 POST + key + 等 2–5 秒，MCU 做不了）。

### 硬件选型（详见 BOM与选型.md）

用户嫌「S3 + 2.8" IPS ¥70」性价比低 → 一路评估：Guition 一体板、7" RGB、香橙派+HDMI、二手手机、墨水屏……最终拍板 **4.2" 黑白墨水屏套装（¥56）+ ESP32**。

- 否决 ST7265 RGB 裸屏（无 GRAM，需主控持续推帧，MicroPython 驱动不了）。
- 否决 ¥38 三色「日历传图」套件（封闭固件，不可编程）。
- 三色 vs 黑白：选**黑白**。三色全刷 15–20s、局部刷基本不可用、双帧缓冲 96KB、底色偏灰；而我们是无符号数字 + 加框表示跌，根本不需要红色。
- 4.26"(800×480) vs 4.2"(400×300)：物理面积后者甚至略大（5393 vs 5176mm²），输的只是 DPI（120 vs 219）。客服确认 4.2" 支持局部刷新 + SSD1619A → 拍板。

## 2026-11-02

### 局部刷新：追了一整轮，结论是这块屏没有局刷

起因：卖家评论说「主控有两个缓冲区，可以发旧画面和新画面，设定 LUT 让变化部分单次刷新」「单色屏不需要抖动就能到黑或白」。按这个思路改了一版驱动（自定义 233 字节波形表 + 0x26 发旧帧 + 0x24 发新帧），然后一路做真机实验，结论全部反过来。

**做了 22 个探针脚本（`tools/_lut1.py` ~ `_lut22.py`），可信结论：**

1. **只有 `0x22=0xF7` 能驱动像素。** `0xC7/0xCF` 是空转：BUSY 跑 840ms，屏一个像素不动。判定方法：先 `0xF7` 刷全黑，再 `0xC7` 刷全白 —— 屏仍是黑。
2. **单独发过 `0x04`（Power ON）之后，后续 `0xF7` 全部失效。** 这是旧 `init_part()` 那句 `0x04` 造成的：所有"局刷不生效"的实验都是在 0x04 之后跑的。去掉 `0x04` 后同样的 `0xF7` 立刻从 840ms 空转变为 5.2s 真驱动。**6 次复现。**
3. **窗口 `0x44/0x45` 在能驱动的模式下被忽略。** 60 行窗口和 300 行窗口耗时一样（5.2s）；窗口只决定 RAM 写到哪里。
4. **`0x26` 是红平面，不是旧帧。** datasheet 表 6-5 明写 `LUTBW=LUTBB`、`LUTWW=LUTWB`，即黑白模式下 R 位不参与 LUT 选择 —— 双 RAM 差分在这颗 SSD1619A 上不成立。
5. **自定义波形表确实进了波形引擎**（`0xC7` + 大表 → 6 行窗口 4.5s，耗时随帧数/组数变化），但它是**整屏统一驱动、与 RAM 数据无关**：8 帧没反应，129 帧把整屏连同黑带一起漂白。所以「改 LUT 画图案」走不通。
6. **`0x1A=0x1E00`（30°C 档）把全刷 5.2s → 2.9s**，出图正常。这是唯一可靠的提速手段。

### 因此改的东西

- `epd42.py` 重写成「结论版」：只保留 `0x24` 写帧 + `0x26` 清零 + `0xF7` 一条路径；
  删掉所有 `0x04/0x01/0x06`；`init(short=True)` 默认用 30°C 短波形；
  `display_Partial()` / `display_Fast()` / `init_part()` 保留为兼容壳（内部都走全刷，注释写明原因）；
  `make_lut/_lut_drive/write_lut` 留作实验工具，文件头明确写「不要接入正式路径」。
- `epaper_main.py`：`show()` 改成「内容真变了才刷」；`render()` 去掉了「同一分钟也重画一次让时间走」的逻辑（那是建立在"局刷不闪"的错误前提上，现在会导致每分钟闪一次）；`quote_sec` 默认 60 → 180。

### 待验证

- 短波形（2.9s）下长时间运行是否会有残影累积。若有，可以把 `clean()` 的触发条件从"仅冷启动"改成"每天一次"。

### 补：寿命护栏（同日 09:40）

查厂家 FAQ（微雪 / 涂鸦开发者文档）拿到两条硬口径：

- 「理想情况下可刷新 **100 万次**」「非局刷产品**刷新间隔建议 ≥180 秒**」；
- 「待机过程中（即刷新操作后）建议设为睡眠模式或断电，**否则长时间处于高电压状态可能烧坏屏幕**」。

对照代码发现两个都没遵守：

1. 板端 `config.json` 里 `quote_sec` 还是 **60**（代码里改的 180 只是"键缺失时的默认值"，不会覆盖已存在的键）。60s = 1440 次/天 = 52.6 万次/年 → 100 万次只够 **1.9 年**，打五折不到 1 年。
2. `epd.sleep()`（`0x10=0x01` 进深睡）写好了但 `epaper_main.py` **一次都没调用**，屏刷完一直挂高压。

改法：

- `show()` 序列改为 `epd_init()` → `epd.display(BUF)` → `epd.sleep()`。深睡只能靠硬件 RST 唤醒，所以每次刷前重走 `init()`（内部先 `reset()`），多花约 230ms。
- 配置护栏：`quote_sec < 180` 一律顶回 180；`full_every` 恒置 1（本屏每次都是全刷，倍数概念无意义）。
- 板端 `config.json` 直接改（用 `tools/sh.py` 走 raw REPL 改 json 再写回，避免整份覆盖掉板上的配置）。
- 网页控制台对应字段的提示文案同步改。

改后账：180s = 480 次/天 = 17.5 万次/年 → 100 万次 ≈ **5.7 年**，打五折 ≈ 2.9 年。

另记一条排查经验：**本地 `firmware/config.json` 与板端 `config.json` 内容可能不同**。改配置别直接上传本地文件，否则会把板上设置冲掉。

- 上传坑：`tools/webrepl.py --put` 传 57KB 的 main.py 会**静默截断到 25KB 且 SHA1 校验还报一致**，别用它传大文件；用 `tools/up.py`（串口 base64 + 回读校验）。

**顺带纠正一个长期误解**：屏上每格显示的是**无符号涨跌幅百分比**，不是点位。`draw()` 取 `v[0]`，而 `quotes()` 存的元组是 `(涨跌幅%, 点位)`，所以屏上看到的是 `0.09  0.12  0.54` 这种，不是 `3602 1414 2410`。设计如此（10-27 最初版就是"代码+无符号涨跌幅+方向条"），点位只是顺带存着。以后跟人对齐口径别说错。

### 踩坑：上传文件名错了，导致上面两次改动全都没生效

现象：改完期货重传后，屏上第三行还是原来的三格，一点没动。

原因：`tools/up.py` 省略第二个参数时**按本地文件名**存到板上，所以

```
python3 tools/up.py firmware/epaper_main.py          # → 板上生成 epaper_main.py（没人 import）
python3 tools/up.py firmware/epaper_main.py main.py  # → 正确，覆盖开机自启的 main.py
```

板上因此同时存在 `main.py`（57302 字节，旧版）和 `epaper_main.py`（58571 字节，新版），跑的是旧的。

**教训一**：判断"改动是否生效"不能看 `updates` 计数或网页 200——旧代码在 `quote_sec=180` 的配置下同样每 180 秒刷一次，看起来完全正常。要看**屏幕上具体某格的内容变没变**，或者直接 `os.stat("main.py")[6]` 对字节数。

**教训二**：`epd.sleep()` 那条改动也因此从未真正在 `show()` 里跑过；之前那条"两轮刷新验证"验证的只是旧代码 + 新配置。真正的集成验证是本轮重传后做的（init 231ms / display 2901ms / sleep，连续两轮）。

## 2026-11-02 11:00 行情页顶栏：涨跌停家数 + 预测全天成交额

### 修正：成交额改成实时累计，不显示外推预测

上线后用户反馈「现在应该是 10000 左右，你显示的有问题」——当时屏上是 23564。核对：**当下实际累计 10030 亿**，23564 是外推的全天预测，恰好 2.4 倍。

改法：`stats()` 里 `est_amount(v[0])` 换成 `v[0]`。`est_amount()` 和 `AMT_W` 权重表保留在代码里（注释掉一行即可切回预测），因为"预测全天"仍有价值，只是不适合和实时值混在同一位置。

**结论记下来**：无标签数字必须放"当下事实"，不能放推算值。要放预测就得带标记或用 `当前/预测` 的形式。

## 2026-11-03 08:20 「刷新太晃眼」→ 0xFF 试完、改分时段

用户反馈每次刷新的整屏黑白翻转太晃眼，问有没有别的刷新方式。这轮把最后一条软件路径试完，结论是**没有**，只能压次数。

### 0xFF 与 0xF7 完全等价

昨天留的最后一个候选 `0x22=0xFF`（bit4 载入 OTP + bit3 display mode 2，SSD168x 标准 partial 值）今天补测：

| 控件 | BUSY 拉高 | 回落到低 | 画面 |
|---|---|---|---|
| `0xF7` | 0 ms | 3169 ms | 出图 |
| `0xFF` | 0 ms | 3166 ms | 出图（无更快、无更少闪） |
| `0xF7`（复测） | 0 ms | 3168 ms | 出图 |

差 3ms，属于同一套波形。结论：这块屏的 OTP 里没有 mode2 的独立波形表，bit3 置位被忽略。**至此 `0xC7/0xCF/0xF7/0xFF` 四个值全部试完，"低闪/无闪"的软件路径不存在。**

### 顺带修掉一个真实缺陷：BUSY 拉高有延迟

测试中出现 `display()` 只花 **25 ms** 就返回（正常 3.1s），紧接着屏被留在半死状态：之后 `0x44` 会让 BUSY 卡 15 s 不回落，再发什么都只得到空转，**只能断电重启恢复**。

根因不在硬件，在驱动：`0x20` 之后 BUSY 不是立刻拉高的（波形引擎有启动延迟），而 `TurnOnDisplay()` 直接进 `ReadBusy()`，`ReadBusy()` 只判"高→低"，如果那一刻还是低电平就立刻返回"刷完了"，于是 `sleep()`（`0x10=0x01`）被发进一个还在跑的波形里。

修法：`TurnOnDisplay()` 先 `wait_assert()`（最多 200ms 等 BUSY 拉高）再 `ReadBusy()`。实测代价 1 ms。这个 bug 平时不显形（正常刷新 BUSY 0ms 就拉高），只有刷新被 Ctrl+C 打断过的屏才会踩到——今天正好踩到，才被抓出来。

### 改成分时段间隔

闪屏消除不了，只能压次数。用户选了"盘中 2 分、其余 10 分"：

- 新增 `in_session()`：工作日 09:00-15:30（含前后 30 分钟缓冲）。
- 新增配置 `quote_sec_off`（默认 600s）；`QuotePage.due()` 每次调用重算 `ttl`，跨过 09:00 / 15:30 立刻切档，不用重启。
- 数量：盘中 195 次 + 早晚 39 次 ≈ **234 次/天**，比原来的 390 次/天（7-20 全天 120s）少 40%。100 万次理论寿命 ≈ 11.7 年（五折 5.9 年）。
- 护栏：`quote_sec >= 120`、`quote_sec_off >= 180` 且不小于 `quote_sec`；网页控制台新增该字段。

### 排查过程里的两个操作性教训

1. **别用 Ctrl+C 打断正在刷新的屏**。REPL 一进去就打断 main.py，若恰好停在 `ReadBusy()` 里，屏会停在波形中途，后面的现象（BUSY 常高、`0x44` 卡 15s、`display` 25ms）会被误读成"排线坏了"。正确做法：先断电重启让 main.py 自己走完一轮，再进 REPL；测试脚本自己要带 `wait_assert()`。
2. **判断"线有没有插好"用内部下拉**：`Pin(7, Pin.IN, Pin.PULL_DOWN)` 读到 1 = 线被外部拉高（活着），读到 0 = 悬空/没接。比反复看屏猜快得多。
3. 板子被碰掉线后重新插，`/dev/cu.usbmodem1101` 会重新枚举；`up.py` 自动找端口有概率落到 `usbserial-110`（不存在）上，直接重跑一次即可，不用改配置。

# 2026-11-03（晚）差分刷新跑通：SSD1619A 双 RAM 差分成立，推翻当日结论

用户贴出淘宝买家评论（@rjxx0011）：「必须自定义 LUT 才能显示」「主控有两个缓冲区，可以发旧画面和新画面，设定 LUT 让变化部分单次刷新」。此前结论「0x26 只是红平面、差分不成立」被要求全部重推。**重推结果：买家说得对，之前失败是三个坑叠加。**

## 三个坑（缺一不可）

1. **LUT 长度写错（主因）**：SSD1619A 规格书 `0x32` 只收 **70 字节**（VS 5组×7 + TP/RP 5组×7）。照 SSD1683/微雪教程写 233 字节，多出的字节被当成后续命令吞掉，波形静默空转 **195ms**，屏一个像素不动。这就是之前判「差分不成立」的原因——表根本没进去。
2. **`0x21=0x40` 旁路了旧帧**：`init()` 一直发 `0x40`（红平面旁路成 0），旧帧从未启用。差分必须 `0x21=0x00`，刷完恢复 `0x40`，否则后续 `0xF7` 全刷冒红。
3. **电压极性写反**：实测 `VSH1(VS=01)` 驱动成**黑**、`VSL(VS=10)` 驱动成**白**。

## 可用配方（_diff9.py 照片验证：上黑下白精确呈现）

```
0x21=0x00 → 0x32 写 70 字节 LUT → 0x24 新帧 → 0x26 旧帧 → 0x22=0xCF → 0x20 → 等 BUSY
LUT：VS=(0,2,1,0,0)（槽0 黑→黑=VSS、槽1 黑→白=VSL、槽2 白→黑=VSH1、槽3 白→白=VSS）
     t[35]=TP0（波形时长）、t[39]=RP0=1
```

槽位按 (旧位,新位) 四组合选波形。总耗时 ≈ `193 + 40.3×TP` 毫秒：TP=40→1.8s、20→1.0s、10→0.6s。BUSY 计时实测 TP=20→1080/1103/1102ms、TP=10→695/714ms，与线性模型吻合（_diff5 标定：TP=0→193ms、10→596、30→1400、63→2723）。

## 工程化落地

- `epd42.py`：新增 `make_diff_lut(tp)` / `display_diff(buf, prev=None)` / `diff_tp`（默认 20）；文件头结论 4、7 重写，总结改为「两条路径」。
- `epaper_main.py`：`show()` 内容变化走差分、`full=True` 走全刷；`Panel.render()` 加 `DIFF_FULL_EVERY=8` 次差分后强制全刷防残影；新增 `diff_count`。

- **遗留**：`display_diff` 的视觉效果待用户拍照确认（驱动自动取 `last_frame` 当旧帧的路径与 _diff9 显式传参等价，但需眼见为实）；TP=10（0.7s）是否留残影待对比，默认保持 TP=20。
